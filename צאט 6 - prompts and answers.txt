כולן מגיעות מ־`node:fs/promises` — כלומר כל אחת מהן **מחזירה Promise**, ולכן כל מה שקורא להן צריך `await`.

בפרויקט שלנו הקבצים הם ESM (`"type": "module"`). ב־ESM אין משתנה `__dirname` כמו ב־CommonJS. `fileURLToPath` ממיר את הכתובת של הקובץ (`file:///C:/...`) לנתיב רגיל ב־Windows (`C:\...`).

### שורות 9–11 — בניית הנתיב לקובץ

מקבל שם קצר, למשל `'courses'`, ומחזיר את הנתיב המלא: `...\data\courses.json`. כך כל שאר הקוד לא צריך לדעת איפה הקובץ באמת נמצא.

### שורות 14–17 — קריאה
```js
export async function readJson(name) {
    const raw = await readFile(filePath(name), 'utf8');
    return JSON.parse(raw);
}
```
- `export` — הפונקציה זמינה לקבצים אחרים (הנתונים שלנו).
- `async` — הפונקציה מחזירה Promise, ובתוכה אפשר לחכות (`await`) לפעולות איטיות.
- `await readFile(...)` — קורא את הקובץ. `'utf8'` אומר לקרוא אותו כטקסט ולא כביטים (buffer).
- `raw` — **טקסט** (מחרוזת), לא מערך. למשל: `'[{"id":"1","name":"Cooking"}]'`.
- `JSON.parse(raw)` — הופך את הטקסט חזרה למערך של אובייקטים. **זה השלב שממיר "קובץ" ל"נתונים" שאפשר לעבוד איתם.**

אם הקובץ לא קיים, `readFile` **זורק שגיאה** (ENOENT), והשגיאה הזו תגיע בסוף לבקרים — שם ה־`.catch()` יהפוך אותה ל־500. בלי `try/catch` כאן, בכוונה: אנחנו רוצים שהשגיאה תעלה למעלה לטיפול.

### שורות 22–28 — כתיבה
```js
export async function writeJson(name, data) {
    const target = filePath(name);
    const temp = `${target}.tmp`;
    await writeFile(temp, JSON.stringify(data, null, 2), 'utf8');
    await rename(temp, target);
}
```
- `target` — הנתיב האמיתי, למשל `...\data\courses.json`.
- `temp` — נתיב זמני: `courses.json.tmp`. **כותבים קודם לקובץ הזמני, ורק בסוף מחליפים.**
- `JSON.stringify(data, null, 2)` — הופך את המערך בחזרה לטקסט. `null` אומר "אל תסנן שדות", ו־`2` אומר "הכנס הזחה של 2 רווחים" — כדי שהקובץ יהיה קריא ובן אדם יוכל לפתוח אותו ולראות שהנתונים אכן נשמרו.
- `await writeFile(temp, ...)` — כותב את כל הטקסט לקובץ הזמני.
- `await rename(temp, target)` — מחליף את הקובץ הישן בקובץ הזמני.

**למה הטרחה של קובץ זמני?** אם השרת נופל בדיוק באמצע `writeFile`, הקובץ האמיתי לא נפגע — הוא עדיין הגרסה המלאה הקודמת. רק אחרי שהקובץ הזמני נכתב עד הסוף הוא מחליף את האמיתי. זה מונע מצב שבו ה־JSON נשאר חצי־כתוב וכל השרת מפסיק לעבוד.

## קובץ JSON = דף נייר כתוב

הקובץ `courses.json` הוא **טקסט**, לא מערך. מבפנים הוא נראה כך:

```json
[
  { "id": "1", "name": "Cooking", "description": "Learn how to cook" }
]
```

זה בדיוק כמו דף נייר: האדם קורא ממנו **טקסט**. גם המחשב קורא ממנו רק טקסט (`string`).
המחשב לא יודע "חפש קורס עם id 1" על דף נייר — הוא יכול רק לקרוא את מה שכתוב.

## אז למה צריך את `JSON.parse` ו-`JSON.stringify`?

אלה **שני "מתרגמים"** בין שני העולמות:

| העולם | הנתונים נראים כמו | הכלי |
|---|---|---|
| הדף (הקובץ) | טקסט: `'[{"id":"1"...}]'` | — |
| העולם של JS (הזיכרון) | מערך רגיל: `[{ id: '1', ... }]` | `JSON.parse` / `JSON.stringify` |

- **`JSON.parse(טקסט)`** — "המתרגם מהדף לזיכרון". לוקח את הטקסט ומקים ממנו מערך אמיתי שאפשר לעבוד איתו (`find`, `push`, `filter`).
- **`JSON.stringify(מערך)`** — "המתרגם מהזיכרון לדף". לוקח מערך ומחזיר טקסט שאפשר לכתוב לקובץ.

## קריאה — שלושה שלבים

```
1. readFile(path)        →  מחזיר טקסט:    '[{"id":"1","name":"Cooking"}]'
2. JSON.parse(טקסט)      →  מחזיר מערך:    [ { id: '1', name: 'Cooking' } ]
3. return המערך          →  הנתונים מוכנים לשירותים
```

בקוד:
```js
const raw = await readFile(filePath(name), 'utf8');  // שלב 1 — טקסט
return JSON.parse(raw);                              // שלב 2 — מערך (שלב 3: מה שמוחזר)
```

## כתיבה — שלושה שלבים, בסדר הפוך

```
1. יש מערך בזיכרון:   courses = [ { id: '1', ... }, { id: '2', ... } ]
2. JSON.stringify →   טקסט מסודר
3. writeFile(path) →  הטקסט נכתב לדף (לקובץ)
```

בקוד:
```js
await writeFile(temp, JSON.stringify(data, null, 2), 'utf8');  // שלבים 2+3
```

## למה ה-`await`?

הדף הוא במגירת כונן, לא ביד. קריאה וכתיבה לוקחות **זמן** (גם אם קטן).
אם לא נחכה, נמשיך לבצע את הפונקציה הבאה לפני שהקובץ בכלל נקרא — והמערך עוד לא קיים.

`await` אומר: "עצור כאן עד שהקריאה/הכתיבה מסתיימת, ורק אז המשך".
לכן הפונקציות הן `async` — הן מחזירות Promise, כמו שליח שאמר "אני עוד מעט מגיע".

## הדוגמה המלאה

```js
// קריאה: דף → מערך
export async function readJson(name) {
    const raw = await readFile(filePath(name), 'utf8');  // קרא את הדף
    return JSON.parse(raw);                              // תרגם למערך
}

// כתיבה: מערך → דף
export async function writeJson(name, data) {
    const text = JSON.stringify(data, null, 2);          // תרגם לטקסט
    await writeFile(filePath(name), text, 'utf8');       // כתוב לדף
}
```

## למה הקובץ הזמני (`courses.json.tmp`)?

בקובץ הישן כתוב כל הנתונים. אם נגיד `writeFile(courses.json, ...)` והוא ייפול באמצע — הדף נמחק ונשאר חצי כתוב, וכל הנתונים אבדו.

לכן: **כותבים לדף חדש (`courses.json.tmp`), ורק כשהדף החדש שלם — מחליפים**. המילה `rename` היא ההחלפה. אם משהו נשבר באמצע — השרת נשאר עם הדף המקורי השלם.

## סיכום במשפט אחד

> **קריאה** = פתח קובץ → קבל טקסט → `JSON.parse` הופך אותו למערך.
> **כתיבה** = קח מערך → `JSON.stringify` הופך לטקסט → שמור לקובץ.

הבהירות עכשיו? אם כן — אמשיך ליצור את שני קבצי ה-JSON ולהמשיך לשלב 3.

## התשובה הקצרה

## למה זה אותו דבר

כשפונקציה היא `async`, **היא תמיד מחזירה Promise**. ואם ה-`return` שלה מחזיר Promise — ה-JS "משטח" אותו אוטומטית:

```js
async function f() { return readCourses(); }        // מחזיר Promise
async function f() { return await readCourses(); }  // מחזיר Promise
```
גם מי שקורא ל-`await f()` מקבל את אותו המערך.

## מה כן שונה מתחת למכסה

יש הבדל **טכני קטן** בשתי נקודות:

**1. "שכבת Promise" אחת פחות**
- `return readCourses()` — מחזיר את ה-Promise המקורי של `readFile` כמו שהוא (עלות אפס).
- `return await readCourses()` — ממתין לו, ואז "עוטף" את הערך ב-Promise חדש ש-`async` יוצרת ממילא. **Promise אחד נוסף שנכנס ויוצא מהתור** (microtask).

העלות: נניח מיקרו־שניות. ביחס לזמן אמיתי של קריאה מהדיסק (מילי־שניות) — **0%**. אין הבדל בזיכרון, אין פתיחת קובץ נוספת, אין כלום.

**2. מקום ה-`try/catch`**
זו הנקודה שהיא באמת חשובה מבחינת **קוד נכון**:

```js
async function f() {
    try {
        return readCourses();       // ⚠️ אם readCourses נכשל — ה-catch לא תופס!
    } catch (e) {
        // כאן לא נגיע
    }
}
```

כאן `readCourses()` מחזיר Promise שנכשל, הוא **לא נזרק** כאן — הוא נזרק רק כשהוא מוחזר החוצה. לכן `try/catch` פנימי לא יראה את השגיאה.

```js
async function f() {
    try {
        return await readCourses(); // ✅ ה-catch כאן תופס את השגיאה
    } catch (e) {
        // כאן נגיע
    }
}
```

כשיש `await`, השגיאה **נזרקת בתוך** ה-`try` ולכן נופלת ל-`catch`.

## ולגבי הקוד שלנו ספציפית

אצלנו, ב-`getAllCourses`, אין `try/catch` פנימי:

```js
export async function getAllCourses() {
    return await readCourses();
}
```

שגיאה בקריאת הקובץ (למשל הקובץ לא קיים) תגיע בכל מקרה לשרשרת ה-`.catch()` של הבקר — בין אם כתבנו `await` ובין אם לא. כלומר, בשבילינו **שתי הצורות עובדות כאן בדיוק אותו דבר**.

## מה הבחירה המקצועית

| מקרה | מומלץ |
|---|---|
| `return הPromise` (סוף הפונקציה, בלי try/catch) | `return readCourses()` — פשוט ונקי |
| `return` בתוך `try/catch` | חייב `await`, אחרת השגיאה לא נתפסת |
| צריך משהו **אחרי** ה-`await` | חייב `await` |

אז אני משנה את הקוד ל-`return readCourses()` (בלי `await`)? זה קצת יותר ישיר — או שנשאיר את `await` בשביל אחידות? שתי האפשרויות נכונות; אני ממליץ על `return readCourses()`, כי אין לנו `try/catch` שם וזה מבהיר שהפונקציה רק מעבירה את ה-Promise הלאה.

## הכלל — מה השתנה בכל בקר

**לפני** (סינכרוני — כל השורות רצות ברצף):
```js
export function getAll(req, res) {
    res.json(coursesService.getAllCourses());   // הערך כבר מוכן

```

**אחרי** (אסינכרוני — הערך עוד לא מוכן):
```js
export function getAll(req, res) {
    coursesService.getAllCourses()              // מחזיר Promise
        .then(courses => res.json(courses))     // "כשיגיע — עשה את זה"
        .catch(err => sendServerError(res, err));
}
```

השלושה שינויים בכל בקר:
1. **`async` לא נוסף** — לא צריך, כי משתמשים ב-`.then()` ולא ב-`await`. הפונקציה נשארת רגילה.
2. **הקוד הישן עבר לתוך `.then()`** — כל הלוגיקה (בדיקת `result.error`, בחירת סטטוס, `res.json`) יושבת בפנים, כי רק שם יש נתונים.
3. **נוסף `.catch()`** — כל שגיאה בקריאה/כתיבה לקובץ מגיעה לכאן, ומחזירה 500.

חשוב: ה-`.catch()` נמצא **בסוף השרשרת**, ולכן הוא גם תופס שגיאה שנזרקת מתוך `.then()` עצמו (למשל `res.json` שנכשל).

| היבט | קובץ ישן | קובץ חדש |
|---|---|---|
| **סגנון** | `const result = ...` ואז שורות רגילות | `service.fn().then(...).catch(...)` |
| **מתי הקוד רץ** | מיד — הערך כבר בזיכרון | "כשיֵדע" — בתוך `.then()` |

| **כשל בקובץ** | לא היה טיפול | **500** דרך `.catch()` |
| **שגיאה גלובלית** | לא היתה מגיעה ל-handler | נרשמת בלוג ומחזירה 500 ללקוח |
| **רותים** | אין שינוי | אין שינוי |
| **`async` בבקר** | — | **לא נוסף** (משתמשים ב-`.then()`) |

בוודאי — ההסבר על השינוי האחרון ב-`app.js`.

## מה היה בשורה הזו

בסוף [app.js](app.js), בתוך `app.listen`:

```js
app.listen(port, () => {
    console.log(chalk.yellow(`Server is running at http://localhost:${port}/`));
    printCoursesToConsole();   // ← השורה הישנה
});
```

`printCoursesToConsole` הייתה **סינכרונית** — היא קראה את המערך שהיה כבר בזיכרון והדפיסה אותו. אין ל-`printCoursesToConsole` שום תוצאה שעלולה "להיכשל" מבחינת Node — ואם משהו כן נכשל, זה לא היה מטופל, פשוט היה נזרק.

## מה עכשיו

פונקציית ההדפסה נמצאת ב-[data/courses.js](data/courses.js) והיא **אסינכרונית**:

```js
export async function printCoursesToConsole() {
    const courses = await readCourses();   // קוראת קובץ מהדיסק
    courses.forEach(...);
}
```

היא קוראת עכשיו את `courses.json` לפני ההדפסה. והקריאה מהדיסק **יכולה להיכשל** — אם הקובץ חסר, פגום, או שאין הרשאה.

## למה זה מסוכן בלי טיפול

```js
printCoursesToConsole();   // ← לא מחכים, לא תופסים
```
הפונקציה מחזירה Promise שהוא יכול להידחות. אם לא מטפלים בזה, ב-Node מודרני התקבל `unhandledRejection` — **אירוע שמפיל את התהליך**. כלומר השרת היה קם, מדפיס "Server is running", ואז נופל מיד אם `courses.json` לא תקין.

## השינוי

```js
printCoursesToConsole().catch(err => console.error('Failed to print courses:', err.message));
```

- **`.catch(...)`** — לוכד את הדחייה של ה-Promise, ומונע ממנה להפיל את התהליך.
- **`console.error(...)`** — מדפיס ללוג שורה ברורה: "Failed to print courses: <השגיאה>". כך העין שלך תראה בלוג שההדפסה נכשלה, אבל השרת **ימשיך לרוץ ויענה לבקשות HTTP**.
- **אין `async` ואין `await`** — `app.listen` נשארת רגילה. אנחנו לא ממתינים להדפסה לפני שהשרת מתחיל, ולא צריך: ההדפסה היא רק נוחות (לראות את הנתונים בטרמינל), לא חלק מתפקוד השרת.

## מה זה נותן בפועל

| מצב | לפני השינוי | אחרי השינוי |
|---|---|---|
| `courses.json` תקין | הדפסה כרגיל | הדפסה כרגיל |
| `courses.json` חסר/פגום | ❌ התהליך נופל מיד | ✅ השרת רץ, הלוג מציג הודעת שגיאה, בקשות מחזירות 500 דרך הבקרים |

זה גם עקבי עם הפתרון כולו: **כשל בקובץ מחזיר 500, לא מפיל את השרת**.
